# 점수 신뢰도 개선 기획안

작성일: 2026-08-20

## 0. 목적

지금까지 나온 모든 후속 작업(UI 통일, sameAs, 네이버 신호, 온톨로지 결합)보다
**먼저** 풀어야 하는 게 점수 신뢰도다. 이유는 단순하다 — 신뢰할 수 없는
점수 위에 기능을 더 얹어봐야 신뢰할 수 없는 제품이 커질 뿐이다. 이 문서는
"무엇을 고칠지"와 "왜 그렇게 고치는지"만 다룬다. 실제 코드 변경은 이 문서가
검토·승인된 뒤 별도로 진행한다.

## 1. 지금 확인된 문제 (전부 실측 근거 있음)

출처: [`real-world-validation-report-2026-08-20.md`](real-world-validation-report-2026-08-20.md)
(실제 공개 페이지 20개, v1+v2 동시 실행), `citegraph-scoring-methodology-v1.md`
§12(자체 감사).

### 1-A. Page Type 분류 실패율 68%

실제 페이지 19개 중 13개가 `UNKNOWN/UNKNOWN`으로 분류됐다. 한국 사이트만의
문제가 아니다 — `stripe.com/docs`, `vercel.com/blog`, `openai.com`,
`wikipedia.org` 같은 구조가 명확한 글로벌 사이트도 전부 UNKNOWN이 나왔다.

**왜 중요한가**: v2의 SEO/GEO Fact score는 Page Type이 확정돼야만 "이 규칙이
이 페이지에 적용되는지"를 판단할 수 있다. UNKNOWN이면 관련 규칙들이 전부
`UNKNOWN`으로 빠지고, 그게 지금 coverage가 낮은(SEO 평균 40%, GEO 평균 30%)
직접 원인이다. 유일하게 `AUTO_ASSIGNED`가 나온 페이지(`techblog.woowahan.com`)
는 coverage도 가장 높았다(74%/64%) — 상관관계가 실측으로 확인됐다.

### 1-B. v1이 페이지 유형을 전혀 모른다

`lib/audit.ts`의 35개 규칙은 페이지가 홈페이지인지 기사인지 구분하지 않고
전부 똑같이 적용한다. 그 결과 실제 데이터에서:

```
toss.im(홈페이지)         GEO 19
musinsa.com(커머스)       GEO 19
oliveyoung.co.kr(커머스)  GEO 17
```

가장 자주 실패하는 규칙 상위 5개 중 4개가 `GEO-TRUST-001`(저자 정보),
`GEO-TRUST-002`(작성일), `GEO-TRUST-004`(발행 주체), `SEO-CONTENT-004`
(갱신 신호)다 — 전부 "이 페이지가 기사여야 의미 있는" 신호다. 홈페이지·
상품 목록 페이지는 원래 저자·작성일이 있을 이유가 없는데 무조건 감점된다.

**중요한 제약**: `lib/audit.ts`는 `rulesetVersion 2026.08.1`로 이번 세션
내내 완전 동결 대상이었다(테스트가 버전 문자열과 35개 규칙 수를 하드코딩
검증). 이 규칙의 판정 로직을 그대로 고치면서 버전 번호를 안 바꾸면
`AGENTS.md`의 "같은 HTML+같은 ruleset version은 항상 같은 점수"가 시간
축에서 깨진다(어제 계산한 점수와 오늘 계산한 점수가 버전은 같은데
달라짐). **이건 이 문서에서 결정할 사안이 아니라 사용자 승인이 필요한
분기점이다** — §3에서 옵션으로 제시한다.

### 1-C. 동일 Fact가 SEO/GEO 두 축에서 중복 배점된다

방법론 자체 감사(§12.3)가 이론으로 지적했던 걸 실측으로 확인했다.
`GEO-TRUST-002`(작성일)와 `SEO-CONTENT-004`(갱신 신호)가 **19개 중 14개
에서 항상 같이 실패**했다 — 둘 다 같은 날짜 신호 하나를 보고 판정하기
때문이다. 날짜 정보 하나가 없으면 SEO와 GEO 점수가 동시에 깎인다. 하나의
결함이 두 번 벌점을 받는 구조다.

### 1-D. Citation Readiness가 너무 쉽게 만점을 받는다

방법론 자체 감사(§12.1, §12.4)가 지적한 것도 실측에서 재현됐다:
`ahrefs.com/blog`가 GEO 100점을 받았는데, 그 안에는 `GEO-CITE-001`(주장-
근거 근접성)이 "claim이 0개면 자동 PASS"인 로직이 포함돼 있다. claim이
0개인 게 좋은 신호가 아니라 "측정을 못 한 것"에 가까운데 만점으로
계산된다. 좋은 페이지가 우연히 만점을 받은 것처럼 보이지만, 판정 조건
자체가 헐거워서 나온 만점일 수 있다 — 구분이 안 된다.

### 1-E. Length heuristic은 의도적으로 UNKNOWN — 문제 아님, 다만 coverage를 계속 깎는다

`AC-SEO-TITLE-LENGTH`, `AC-SEO-META-LENGTH`, `AC-SEO-BODY-AMOUNT`는
calibration profile이 없어서 지금 **항상 UNKNOWN**을 반환한다. 이건
v1처럼 20~65자 같은 근거 없는 고정 threshold를 쓰지 않겠다는 의도된
설계이지 버그가 아니다. 다만 이것도 coverage를 깎는 요인 중 하나이므로,
"왜 coverage가 낮은가"를 설명할 때 1-A와 섞어서 착각하면 안 된다.

## 2. 원인별 해결 방향 (코딩 전 검토용, 아직 미확정)

### 2-A. Page Type 분류기 신호 보강 — 영향 가장 크고 리스크 가장 낮음

- 지금 신호가 약한 실제 사례(홈페이지지만 Organization schema 없음, 문서
  페이지지만 schema 없음)에 대응하는 신호를 추가한다: `og:type` 메타 태그,
  breadcrumb(`BreadcrumbList` schema 또는 `nav[aria-label*=breadcrumb]`),
  `<article>` 없이도 본문 하나로 구성된 블로그 목록 페이지 패턴 등.
- **하지 않을 것**: SATURATION_FLOOR(7)를 낮추거나 confidence 임계값
  자체를 조정하는 것. 이건 calibration 절차를 우회하는 것과 같다 — 신호를
  더 모으는 것과 확정 기준을 낮추는 것은 다르다.
- 이미 있는 fixture 15개 + 실제 페이지 20개 양쪽에서 회귀 없는지 검증
  필수(지난번 F08/F15가 깨졌다가 가드 추가로 복구된 전례 있음).

### 2-B. v1의 page-type 무지 문제 — 결정이 필요한 분기점

세 가지 옵션이 있고, 이 문서는 하나를 고르지 않는다. 사용자 승인이 필요하다.

| 옵션 | 내용 | 장점 | 단점 |
|---|---|---|---|
| B1. v1 동결 유지, 아무것도 안 함 | 지금처럼 v1은 "레거시, 알려진 한계"로 남긴다 | 안전, 결정론 계약 안 깨짐 | 지금 실제로 사용자에게 보이는 점수는 계속 부정확함 |
| B2. v1을 명시적으로 버전업(`2026.08.2` 등) | 페이지 유형 인지를 추가하고 버전을 새로 발급 | 문제 해결, 계약 안 깨짐 | v1 "35개 규칙 동결"이라는 지금까지의 정체성이 바뀜 |
| B3. v2를 공식 점수로 승격, v1은 legacy 표시로 전환 | UI에서 v2를 주 점수로, v1은 "이전 방식(참고용)"으로 격하 | 이미 v2가 구조적으로 이 문제를 풀도록 설계돼 있음 | v2 coverage가 아직 30~40%라 지금 승격하면 "빈 점수"가 주력이 됨 — 2-A 먼저 끝나야 함 |

**제출자 의견**: B3가 방향상 맞다고 본다(v2가 이 문제를 풀려고 설계된
구조이기 때문). 다만 2-A(Page Type 개선)로 coverage가 충분히 오르기
전에는 시기상조다. 그래서 **지금은 B1(현상 유지)로 두고, 2-A 완료 후
coverage 수치를 보고 B3 전환 시점을 다시 논의하는 걸 제안한다.**

### 2-C. 중복 Fact 배점 — Rule Registry 조정으로 해결

`GEO-TRUST-002`/`SEO-CONTENT-004`처럼 같은 Fact를 보는 rule 쌍을 찾아서,
v2 Registry에서는 "하나의 Fact, 하나의 축에서만 배점"으로 재배열한다.
v2는 이미 Evidence Layer가 Fact를 1회만 저장하는 구조라(방법론 §14.4)
설계상 이 문제를 피하도록 돼 있는데, 실제로 GEO_FACT와 SEO 양쪽에서 같은
`date.signal`을 각자 다른 질문으로 쓰고 있는지 규칙 하나하나를 다시
점검해야 한다.

### 2-D. Citation 판정 조건 강화 — 가중치보다 조건이 먼저

`AC-GF-CITEURL`/`AC-GF-CITEPROX`가 "claim 0개 → N/A"는 이미 v2에서
맞게 처리돼 있다(방법론 §12.4 문제를 v2 설계 시점에 이미 고쳤음 —
`citation.relation` FactType의 `NO_CLAIM` 분기). 문제는 **v1에 아직
이 수정이 없다**는 것이다. 이것도 2-B 결정에 따라 처리 범위가 달라진다.

## 3. 우선순위 제안 (순서, 확정 아님)

```
1순위: 2-A Page Type 분류기 신호 보강
        → 실제 페이지 20개 + fixture 15개로 재검증, coverage 변화 수치화
2순위: 2-C 중복 Fact 배점 점검 (v2 Registry, 코드 변경 적음, 리스크 낮음)
3순위: 2-B 분기점 재논의 (2-A 결과 수치를 보고 사용자가 결정)
4순위: 2-D는 2-B 결정에 종속 — v1을 안 건드리면 자동으로 범위 밖
```

## 4. 완료 기준 (검증 계획)

- Vitest 전체 통과, typecheck/lint/build 통과 (기존과 동일)
- fixture 15개 회귀 없음(F08/F15 같은 재발 케이스 특히 확인)
- 실제 페이지 20개 재실행 후 다음을 비교 리포트로 남긴다:
  - Page Type UNKNOWN 비율 변화(68% → ?)
  - SEO/GEO Fact coverage 평균 변화(40%/30% → ?)
  - 이전에 UNKNOWN이었던 페이지 중 몇 개가 PROVISIONAL/AUTO_ASSIGNED로
    바뀌었는지 개별 확인(회귀 없는지)

## 5. Codex 검토 요청 사항

1. §2-A의 신호 추가안이 기존 Page Type 로직(`lib/v2/page-type.ts`)의
   가중치 체계와 충돌하지 않는지 — 특히 이전에 겪은 "새 신호가 기존 확정
   신호를 잠식해 오히려 UNKNOWN으로 떨어지는" 패턴이 재발할 여지가 있는지
2. §2-B의 세 옵션 중 놓친 옵션이 있는지, B3 전환 기준(coverage 얼마
   이상이면 안전한지)에 대한 의견
3. §2-C에서 실제로 중복인 Fact/Rule 쌍이 이 문서에 적은 것 말고 더
   있는지 Registry 전체를 훑어서 확인 가능한지
4. §4 완료 기준에 빠진 검증이 있는지

이 문서에 대한 검토 의견을 받은 뒤에만 개발을 시작한다.
